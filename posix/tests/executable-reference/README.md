# Native signed executable references

This opt-in integration fixture exercises the actual AppCore API, libc fork/
spawn runtime, capability broker, signed installed package graph and native
image replacement. It is not part of the production image or SDK.

Build from the mochiOS workspace root with a matching native toolchain and an
SDK assembled from the current libc runtime (published shared.9 is too old):

```sh
mmake native-test-services
python3 services/posix/tests/executable-reference/build.py \
  --sdk-metadata out/newlib-port/sdk/share/app-build.json \
  --target-directory out/native-fixtures/target
python3 services/posix/tests/executable-reference/stage.py \
  --stage /absolute/path/to/private-vm-stage \
  --sdk /absolute/path/to/sdk \
  --native-directory out/native-fixtures/target/x86_64-unknown-mochios/release \
  --msign out/mmake/host-tools/release/msign
```

`stage.py` only writes the supplied private staging directory. It creates the
three fixture packages and development built-in verification records; it never
writes a disk, modifies the installed OS, or publishes a package. Include these
files in a development VM image using the normal image assembly/signing path.
The image must also include matching capability, user, POSIX, filesystem, logger,
core and the feature-built service-manager, each with its own matching manifest
and verification record. The immutable trusted-role index also requires the real
Msh, Terminal, Workspace, Secure UI, Input, Compositor and Drivers images. The
ordinary Signature and Package services must be included for broker bootstrap.
Do not remove trusted-role checks or substitute fixture binaries for these roles. Use an empty private Data volume for each run.

The service-manager feature starts the ordinary filesystem, POSIX and account
services before the existing headless test launcher. The trusted launcher uses
its declared `fs.read.all` only to request a normal application launch. The
actual probe has **no `fs.read.all`** and no hard-coded kernel grants. Do not add
such a permission to make this test pass. No helper is loaded from initfs.

The probe checks own-package and publisher-pinned external helper selection,
missing/invalid aliases, ABI mismatch, refusal of a child requiring more
capabilities, empty child environment, pipe output, stable repeated wait, and
an explicitly mapped FD 7 with verified file contents, and a bidirectional
`SOCK_SEQPACKET` IPC roundtrip through delegated FD 3 (the WebKit transport). It also catches failure
to preserve signed Bundle startup keys across fork and to decode packed IPC
reply lengths correctly. The external helper is an exported application binary
inside a library package, rather than an implicitly executable library.

Success requires the exact `EXE-API PASS` line in the Data volume's
`/tmp/executable-api-results.log`, with no `EXE-API FAIL`. Launcher exit status,
a successful boot, a window or a timeout alone must never count as a pass.
Read this file directly from the VM volume; release logging may be disabled.

The SDK metadata must use the current runtime. The image tools require the
existing development System-signing and UEFI-signing configuration; production
keys are never generated by this fixture. The fixture services and feature-specific service-manager
binaries are built into the isolated target directory; they must never replace
the ordinary desktop service-manager in the normal Cargo output.

The launcher optionally reads `/system/resources/native-test.conf` from the
private, immutable System image. Defaults run the executable-reference probe.
For another signed application integration fixture, use:

```text
application=/system/applications/Terra.app/entry.elf
result=/tmp/terra-engine-results.log
pass=TERRA-ENGINE PASS
fail=TERRA-ENGINE FAIL
timeout_seconds=1260
```

Only a canonical System application entry and a single file under `/tmp` are
accepted. This changes the development fixture's launch target, not application
authority or capabilities. The launcher retains one reader and polls twice a
second. Only complete result lines count; a failure wins over a pass, and a
timeout exits unsuccessfully. The host must independently verify the result
from a coherent VM disk snapshot.

To assemble and run a fresh signed A/B image with Secure Boot using the existing
OS tools (requires the normal development-signing configuration):

```sh
python3 services/posix/tests/executable-reference/image.py \
  --native-directory out/native-fixtures/target/x86_64-unknown-mochios/release \
  --output out/native-fixtures/image-build
python3 services/posix/tests/executable-reference/run_vm.py \
  --image out/native-fixtures/image-build/image/ab-layout.img \
  --directory out/native-fixtures/vm
```

Both commands require fresh output directories below `out/`. The image builder
uses the normal runtime, services, core, disk extension, signed bootloader and
System-image signing tools from `mmake native-test-services`. An optional
`--overlay` supplies a reviewed additional signed fixture package and immutable
launcher configuration. `--system-libraries` stages the normal catalog-verified
System libraries and existing fonts. No collector, new trust root, bypass of
capabilities or real-device writes are involved.

The observer uses KVM with 6 GiB and two vCPUs. Every ten seconds it pauses the
VM, flushes its virtual disk and extracts only the Data partition, then resumes
it in a `finally` block. Its private disk is owned by this runner; do not attach
another observer or writer to it. Complete success/failure lines determine the
result, with optional `--required-line` evidence for additional integration
fixtures. This is a mechanism test, not visual or startup-performance approval.

The VM exposes a debugger only through its private local `gdb.sock` Unix socket.
Acquire an exclusive `flock` on the VM directory's `capture.lock` while using
the debugger, so disk observation cannot resume the guest during inspection.
Attach after UEFI has finished and the kernel has started; this host QEMU build
can abort when GDB accesses CPU state during firmware SMM initialization.

Observer regression checks (run from the OS workspace root):

```sh
python3 -m unittest discover -s services/posix/tests/executable-reference -p test_observer.py
rustc --test --edition 2024 services/posix/tests/executable-reference/launcher_config.rs \
  -o out/native-fixtures/launcher-config-test
out/native-fixtures/launcher-config-test
```

The observer test checks extraction against a real qcow2 file with different
neighbouring contents. A bounded raw view over qcow2 preserves the exact
partition range; sparse output avoids rewriting the entire mostly empty Data
partition at every observation.
